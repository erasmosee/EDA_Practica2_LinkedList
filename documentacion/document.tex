\chapter{Introducción}

En esta práctica hemos implementado una estructura basada en listas enlazadas, concretamente listas doblemente enlazadas circulares.

A partir de la clase común \texttt{DoubleLinkedList} hemos creado una variante sin orden \texttt{UnorderedDoubleLinkedList} y otra con orden \texttt{OrderedDoubleLinkedList}.

El nodo \texttt{Node<T>} guarda referencias a anterior y a siguiente, lo que nos permite recorrer la lista de manera bidireccional conectando el primero con el ultimo.

La lista ordenada tiene la resctriccion de que ha de implementar elementos que implementen \texttt{Comparable<T>}, mientras que la no ordenada tiene mas libertad en cuanto a los elementos que almacena.

Se han realizado pruebas tanto con enteros y objetos \texttt{Persona} para finalmente implementarlo en la practica 1 de Atores y peliculas.

\chapter{Descripción de las estructuras de datos principales}

Sobre las listas doblemente enlazadas, podemos afirmar que si la lista esta vacia, no hay ningun nodo, por lo que \texttt{first == null} y el contador vale cero \texttt{count == 0}. En caso de tener elementos cada nodo desde el primero apuntara tanto al siguiente como al anterior, de manera que el ultimo es accesible desde el primero y el primero desde el ultimo formando un circulo.
En los casos en los que solo hay un nodo, este sea puntara a si mismo. El contador nos permite saber el numero de elementos de manera directa \texttt{O(1)} sin tener que recorrer toda la lista contando elementos, a coste de que cada vez que añadimos o quitamos un elemento de la lista agregar una modificacion al contador.
Cada vez que se añade o se retira un elemento de la lista, hay que actualizar los enlaces del elemento nuevo y de los elementos que rodean al nuevo elemento para que no se rompa la lista.

  //Elimina el primer nodo, actualiza {@code first} y los enlaces entre el nuevo primero y el último.
  public T removeFirst() {
    Node<T> aux;
    if (isEmpty()) {
      throw new NoSuchElementException();
    } else {
      aux = first;
      if (isAlone()) {
        first = null;
      } else {
        first.prev.next = first.next;
        first.next.prev = first.prev;
        first = first.next;
      }
      count--;
    }
    return aux.data;
  }

  //Inserta {@code elem} en orden si no existe. {@code n} es el tamaño de la lista.
  public void add(T elem) {
    if (isEmpty()) {
      addWhenEmpty(elem);
      return;
    }
    Node<T> last = first.prev;
    if (elem.compareTo(first.data) == 0 || elem.compareTo(last.data) == 0) {return;}
    if (elem.compareTo(last.data) > 0) {
      insertAdd(elem, last, first);
      return;
    }
    if (elem.compareTo(first.data) < 0) {
      insertAdd(elem, last, first);
      actualizarFirst(first.prev);
      return;
    }
    Node<T> current = first;
    while (current.next != first && elem.compareTo(current.next.data) > 0) {current = current.next;}
    if (elem.compareTo(current.next.data) == 0) {return;}
    insertAdd(elem, current, current.next);
  }

  //Busca un elemento igual a {@code elem} o lo inserta en orden. {@code n} es el tamaño de la lista.
  public T findOrAdd(T elem) {
    if (isEmpty()) {
      addWhenEmpty(elem);
      return elem;
    }
    int comparacionConPrimero = elem.compareTo(first.data);
    if (comparacionConPrimero == 0) {return first.data;}
    if (comparacionConPrimero < 0) {
      insertAdd(elem, first.prev, first);
      actualizarFirst(first.prev);
      return elem;
    }
    Node<T> last = first.prev;
    int comparacionConUltimo = elem.compareTo(last.data);
    if (comparacionConUltimo == 0) {return last.data;}
    if (comparacionConUltimo > 0) {
      insertAdd(elem, last, first);
      return elem;
    }
    Node<T> current = first;
    while (elem.compareTo(current.next.data) > 0) {current = current.next;}
    int comparacionConSiguiente = elem.compareTo(current.next.data);
    if (comparacionConSiguiente == 0) {return current.next.data;}
    insertAdd(elem, current, current.next);
    return elem;
  }
\end{lstlisting}

\section{\label{merge}merge}
\begin{lstlisting}[language=Java]
  //En recorridos e inserciones: fusiona ambas listas en orden. {@code n} y {@code m} son sus tamaños iniciales; combinar elementos iguales añade el coste de {@code combinarCon}.
  public void merge(DoubleLinkedList<T> lista) {
    if (lista == null || lista.first == null) {return;}
    if (isEmpty()) { // si nuestra lista esta vacia se clona con la del parametro
      first = lista.first;
      count = lista.count;
      return;
    }
    Node<T> p1 = first; // creamos los punteros para que recorran las listas
    Node<T> p2 = lista.first;
    int cuantos1 = count; // guardamos en auxiliares la cantidad total de elementos de cada lista.
    int cuantos2 = lista.count;
    while (cuantos1 > 0 && cuantos2 > 0) { // fusionamos ambas listas
      if (p1.data.compareTo(p2.data) < 0) { // si esta ordenado, seguimos comprobando
        p1 = p1.next;
        cuantos1--;
      } else if (p1.data.compareTo(p2.data) == 0) {
        combinarIguales(p1.data, p2.data);
        p1 = p1.next;
        p2 = p2.next;
        cuantos1--;
        cuantos2--;
      } else { // si no reemplazamos
        insertAdd(p2.data, p1.prev, p1); // si esta desordenado, añadimos en nuestra lista el elemento anterior a p1.
        if (p1 == first) { // comprobamos si hemos añadido un elemento antes del first
          actualizarFirst(first.prev); // p2 pasa a ser el nuevo first de nuestra lista
        }
        p2 = p2.next; // actualizamos el puntero de la lista del segundo 
        cuantos2--;
      }
    }
    // si aun quedan elementos en la otra lista, entonces es que quedan los mayores, por lo que irian al final.
    while (cuantos2 > 0) {
      insertAdd(p2.data, first.prev, first); // insertamos cada elemento al final en orden
      p2 = p2.next;
      cuantos2--;
    }
  }
\end{lstlisting}

La practica nos ha servido para ver el potencial que tienen las listas enlazas cuando cumplen los criterios de estar doblemente enlazadas y de ser una lista circular, frente a listas enlazadas mas simples, si bien es cierto que la memoria usada por las listas doblemente enlazadas es bastante superior a las listas enlazadas de una sola direccion, consideramos que es un coste asumible a la hora de proceder a trabajar con dichas listas.

\section{\label{dificultades}dificultades}

Durante el desarrollo de la practica 2, hemos ido probando distintas formas de integrarla con la practica 1, pues era un objetivo que ya teniamos en mente desde el principio.
En un primer momento antes de implementar el metodo \texttt{merge}, procediamos a volcar la informacion leida de los ficheros a un hashmap, ordenarlo y posterioremente lo volcabamos a una \texttt{OrderedDoubleLinkedList}, como es de suponer, la velocidad de insertar elementos ordenados en una lista ordenada es O(1) siempre que compares previamente el elemento a insertar con el first y con el prev.
Mas tarde, tuvimos un metodo merge no cuadratico, y fue cuando pasamos empezamos a tener pequeñas listas sacadas una de cada fichero de año, las cuales obteniamos aun mediante hashmap, pero que las volcabamos a OrderedDoubleLinkedList para luego proceder a mergearlas en una unica lista OrderedDoubleLinkedList, en este momento fue cuando el programa paso de tardar de 12 minutos a 70 segundos en procesar la lista completa de actores y peliculas.
Una vez llegados a este punto en el que el programa tardaba "solo" 70 segundos, y lo comentabamos contentos pues sabiamos de donde veniamos, empezamos una pequeña competicion por hacer un merge decente.
Mientras unos estaban con el merge, otros estaban dilucidando como reducir esos 70 segundos con los que en ese momento estabamos contentos, por lo que empezamos a pensar en hacer merge de listas mas pequeñas a medida que leiamos de cada fichero.
En un principio pensamos que cada 1000 elementos podiamos hacer un merge por lo que modificamos el lector para que cuando llevase X elementos mergease lo leido a una \texttt{OrderedDoubleLinkedList} de los datos de ese año, para una vez finalizado el fichero de año, mergearlo con la \texttt{OrderedDoubleLinkedList} global.
Ya que teniamos un numero, decidimos empezar a variarlo y comprobar como respondia el codigo, para nuestra sorpresa, el numero bueno no era mil elementos, si no 127, y es en ese punto donde descubrimos que se realizaban el menor numero de operaciones \texttt{compareTo} en nuestro codigo.
ni que decir que cuanto mas aproximabamos el numero de lotes a 127 mas rapido se procesaba el codigo, las ultimas pruebas ya fueron para ajustar milesimas, es cuando habiamos llegado a menos de 5 segundos.
